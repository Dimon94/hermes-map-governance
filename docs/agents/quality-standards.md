# Quality Standards

用途：代码审查、重构和交付前自检。

## 1. 报告顺序

1. Findings。按严重度排序。
2. Coding。检查局部正确性、类型、错误、测试和坏味道。
3. Architecture。检查所有权、依赖、interface 和持久状态。
4. Spec。独立核对需求和验收标准。
5. Verification gaps。记录未运行测试、未覆盖路径和剩余风险。

每个 finding 必须包含：

- 具体文件和行号。
- 可触发场景。
- 可观察影响。
- 证据。
- 最小修复方向。

没有证据时写 Unknown，不报告为缺陷。

## 2. 严重度

- P0：正在造成不可逆数据损坏、严重安全问题或全面不可用。
- P1：主路径必然失败、权限绕过、持久状态污染或外部合同破坏。
- P2：特定条件下错误、恢复失败、明显性能回归或高扩散维护风险。
- P3：局部清晰度或一致性问题，当前不破坏行为。

严重度由影响和可触发性决定，不由规则名称决定。

## 3. 正确性

检查：

- 输入边界是否完整。
- 状态和身份是否由正确 owner 校验。
- 成功条件是否断言业务 outcome。
- 失败是否显式且可恢复。
- 并发、重试和幂等是否保持不变量。
- 持久写入是否原子且可读回。
- 外部副作用是否可能重复。

## 4. 简洁性

应用：

- KISS：选择满足需求的最简单方案。
- YAGNI：删除当前需求不使用的扩展点。
- DRY：消除重复规则，不抽象偶然相似语法。
- SOLID：作为诊断工具，不作为增加层级的许可。

每个新增实体都要通过必要性检查。每个可疑模块都要通过 deletion test。

## 5. 坏味道

- 平行真相。
- 错误 owner。
- 重复业务规则。
- 循环依赖。
- Shotgun surgery。
- Divergent module。
- Shallow wrapper。
- Leaky interface。
- Speculative generality。
- Silent fallback。
- Test past interface。
- 无删除条件的兼容层。

发现坏味道时说明当前影响。不要把审美偏好写成 finding。

## 6. 测试质量

- 检查错误实现是否会失败。
- 检查是否穿过 public interface。
- 检查断言是否关注结果和不变量。
- 检查 mock 是否隐藏真实合同。
- 检查 fixture 是否可能访问真实外部系统。
- 检查时间、随机和并发是否可重复。
- 检查是否缺少关键负向路径。

## 7. 完成条件

Review 只有在以下条件成立时完成：

- 当前 diff 每个语义边界已检查。
- Coding 和 Architecture 两轴均已覆盖。
- Spec 独立核对。
- 每个 finding 可由证据复现。
- 无 finding 时仍列出验证缺口和剩余风险。
